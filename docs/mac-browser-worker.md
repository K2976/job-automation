# MacBook browser worker — local setup

The worker (`worker/worker.py`) is an outbound-only client. It connects to the deployed Render
API, authenticates, claims tasks, runs Playwright locally, and reports results. It does **not**
require you to run the FastAPI backend locally (§26).

## Configure

Copy the template and fill it in (never commit `.env.worker` — it's gitignored):

```bash
cp .env.worker.example .env.worker
```

| Variable | Meaning |
| --- | --- |
| `API_BASE_URL` | The deployed Render API base URL (https). |
| `WORKER_AUTH_TOKEN` | Shared token — must equal `WORKER_AUTH_TOKEN` on Render (§13). |
| `WORKER_ID` | Optional; defaults to `mac-<hostname>`. |
| `WORKER_POLL_SECONDS` | Optional poll cadence (default 5). |
| `WORKER_IDLE_MAX_SECONDS` | Optional idle back-off cap (default 30). |
| `WORKER_HEADLESS` | Optional; `false` to watch the browser (default headless). |

**No LLM keys, no database URL, no passwords** — semantic answers are generated by the Render
API (§28), and all state lives behind the API.

## Run

```bash
docker compose up browser-worker      # recommended (Docker) — see docker-browser-worker.md
# or, natively (needs `playwright install chromium` once):
API_BASE_URL=… WORKER_AUTH_TOKEN=… PYTHONPATH=backend python -m worker.worker
```

The worker will:

1. connect to the Render API and authenticate,
2. heartbeat (so the site shows it Online),
3. poll and **claim** one `QUEUED` task at a time,
4. download the tailored résumé, drive the existing V3 runner in a fresh Chromium context,
5. report the outcome back,
6. back off when the queue is empty, and stop cleanly on `Ctrl-C`.

## Lifecycle

- **Online/offline** shows in the Applications tab. When the worker is off, the rest of the
  site keeps working; only automated applications are unavailable (§31/§32).
- **Crash safety:** if the worker stops mid-task, the API recovers the task — re-queued if no
  submit was granted, or flagged `SUBMISSION_UNCERTAIN` if it might have submitted (§18).
